# AKAB Portal — notes for Claude Code

Portal for AKAB Informatique (MSP, Lanaudière): internal team first, clients next.
Brand follows akab.ca: ink `#0a0a0b`, paper `#f4f4f1`, gold gradient
`#ffe24a → #ffce1a → #f59410`, Bricolage Grotesque (display) + Instrument Sans
(body). Logo: `src/assets/akab-logo.webp` through `src/components/brand/Logo.tsx`
(`Logo` full, `LogoMark` bars + cursor, `Wordmark` lettering). The word AKAB as a
brand mark is always the `Wordmark` image, never typed in a font. Dark theme by default.
Any UI or design work (new page, section, component, restyle): load the
`design-taste-frontend` skill first and follow it. French by default, every text in `src/i18n/fr.ts`
**and** `src/i18n/en.ts`.

## Branches

- `master` is production. Work on `feat/...` / `fix/...` branches, merge when `npm run build` and `npm test` pass.
- `master` is the only branch on GitHub; no other branches or tags are kept.

## Commands

- `npm run dev` — web :5173 + API :3001 (PGlite in `.data/`, delete it to reset)
- `npm test` — API tests (vitest, in-memory PGlite). Add a test for every new route/permission.
- `npm run build` — type-check (web + server) and bundle. Must pass before committing.
- `npm run db:generate` — after changing `server/db/schema.ts`, generates a migration in `drizzle/` (commit it). Migrations run at startup.

## Adding a module

1. `shared/permissions.ts`: add the module and its rights (labels FR/EN). The Administrator role gets every staff right automatically.
2. API: new file in `server/routes/`, mount it in `server/app.ts`, guard every route with `requirePermission("<key>")` (and `requireStaff` for staff-only areas).
3. UI: page in `src/pages/`, entry in `src/modules/registry.ts` (remove `upcoming`), route in `src/App.tsx`.
4. Tests in `tests/`.

## Weekly meeting (Rencontre hebdomadaire)

Administration tab `/meetings`, used live during the Monday team meeting (lists refresh every 10–30 s).

- Rights: `meetings.view` (see the page) and `meetings.manage` (change anything on it). Administrators only by default.
- API: `server/routes/meetings.ts`, mounted at `/api/meetings`. UI: `src/pages/meetings/` (`MeetingsPage`, `Points`, `Projects`, `Absences`).
- Sections, top to bottom:
  - **Points à discuter** (`meeting_points`, half width): a fast text field; checked off when settled; settled ones stay visible 7 days. A click opens the point's notes (`meeting_point_notes`, oldest first, `/points/:id/notes`). A point can be put off (`snooze_until`, YYYY-MM-DD Québec, after today: off the list until that day; `GET /points/later`, "Reportés (n)" to bring one back) or archived (`archived_at`; `GET /points/archive`, the "Archives" toggle of the same card, with a search; restore = back on the list). Migration `0045`. Beside it, **La semaine** (`GET /week?from=YYYY-MM-DD`, `Week.tsx`): Monday–Sunday; a day shows the team planning blocks (as `asSeen`/`seesFull` allow), absences, open tickets due and projects due that day, and Québec holidays. Events (`meeting_events`, migrations 0041–0042: date, optional HH:MM start/end, title, note, optional person, optional ticket — only its id is taken from the browser, number/title read from the ticket source) and absences are added/edited from the selected day (`/events` POST/PUT/DELETE, `meetings.manage`).
  - **Billets en retard et à échéance cette semaine** (`GET /overdue`): open tickets from the ticket source (Autotask, or sample data locally) past due, or due by the end of Friday in Québec time (`fridayEnd` / `fridayDate`; on a weekend, the coming Friday). Shown as two gauges (overdue / due by Friday), green → red at 25, critical at 35; under each, every technician (and the unassigned tickets) as a chip in the same colors — picking one shows their count on the gauge. A third gauge (`stray` in `/overdue`): open tickets with no technician whose status is past "new" (any due date), red at 5, critical at 10, chips per status. Clicking a gauge opens a short list of its tickets (for the person picked, if any); clicking the list opens Tickets with the same filter: overdue `view=due&due=overdue`, this week `view=all&statusKind=<open kinds>&due=week` (portal filter: not overdue, due by `fridayEnd`), stray `view=unassigned&statusKind=<open kinds but new>`, plus `assignee=<id|none>`. The three gauges count only some ticket queues: by default every queue whose name does not contain "alert" (monitoring alerts), or the ones a `meetings.manage` user picked (`PUT /gauge-queues`, stored in `integrations` provider `meetings`, `gaugeQueues`; `null` = default); their links add `queue=`. Monitoring alerts (`isAlert` in `server/routes/tickets.ts`: alert queue, or a source containing alert/monitor) are left out of those gauges, their links (`alerts=0`) and La semaine; a fourth gauge lists the open alerts (newest first, red at 10, critical at 20): a click opens the ticket over the meeting (ticket workspace `ws.open`, closing it comes back to the refreshed meeting; La semaine ticket links do the same), "Résolu" sets `completeStatus` through `PATCH /api/tickets/:id` (`tickets.edit`); Tickets filter `alerts=1` shows only them.
  - **Projets en cours** (`meeting_projects`, `meeting_project_members`, `meeting_project_notes`): client (free text), due date (YYYY-MM-DD), team members (active staff only), notes newest first. Done projects are hidden behind "Terminés".
  - Absences (`meeting_absences`): one row per person and date range (both days included), kind `vacation | sick | training | personal | other`. No month calendar any more: they show and are added in **La semaine** at the top (`AbsenceDialog` in `Absences.tsx`).
  - **Tendances des billets** (under the projects, `Trends.tsx`, `GET /trends?weeks=4..52`): week by week (Monday, Québec) created / resolved / net / open at the end of the week / average and median resolution time / resolved within 24 h, from `TicketSource.history(since)` (light rows: created and completed dates; Autotask query cached 30 min, sample data seeded by the day), same queues as the gauges, no monitoring alerts. Open at a past moment = open now − came in since and still open + already there and resolved since. The last 7 days are compared with the same 7 days 1…N weeks back (slider, quick chips, or a click on a week in the chart or table).
  - **Projets en cours** will be linked to the sidebar **Projets** section (upcoming module `projects`, own sidebar section) once it is built.
- Absences are shared with the Tickets planning calendar: `GET /api/planning/absences` (same access rules as `/planning/calendar`) hatches absent days in `WeekCalendar`, and creating or moving a block on an absent day returns the `absent` warning (still saved).
- Migrations `0023`–`0026`. Tests: `tests/api.test.ts` ("weekly meeting: …") and `tests/meetings.test.ts` (Friday cut-off).

## Pause café (coffee break)

Team › Pause café (`/breakroom`, right `breakroom.use`, technicians by default; API `server/routes/breakroom.ts`, UI `src/pages/breakroom/BreakroomPage.tsx`).
- **30 minutes a day** (Québec day): the page posts `/beat` every 30 s while it is visible; the time since the previous beat counts when it is a minute or less (`breakroom_usage`, migration 0053). Once used, every route but `/status` and `/beat` answers 403 `break_over` and the page shows "La pause est terminée" until tomorrow.
- **Échecs** (chess, `chess.js` on both sides): colleagues online = staff with a session active in the last 3 min (`GET /online`). Invite (`POST /chess`, notification `breakroom.invite` → `/breakroom?game=<id>`; one open game per pair), the invited one accepts or declines (`/respond`); the one who invited plays white. Every move is checked on the server (`/move` `{ from, to, promotion? }`; the game is replayed from its PGN so repetition counts; a concurrent change answers `game_changed`); ends on checkmate, stalemate, draw or `/resign` (which also cancels an unanswered invitation). `chess_games` (FEN + PGN, migration 0053; the earlier checkers table is dropped in 0052). The board polls every 1.5 s. Tests: `tests/api.test.ts` ("coffee break").
- **Complots** (Rikki Tahta's bluffing game, Ferti; French Coup): `server/lib/complots.ts` is the rules engine (pure functions on a JSON state: `newGame`, `play`, `tick` for timeouts — answer 15 s, turn 90 s, choices 30–45 s —, `leave`, `viewFor` hides other players' cards); tests `tests/complots.test.ts`. Tables `complots_games` (migration 0056: host, `seats` with answers, the 5 `chars`, `state`, `rev` for concurrent writes; one change at a time per table in-process). Routes `/api/breakroom/complots` (list, create + `breakroom.complots` notification, `/respond`, `/start` by the host with 2–6 who said yes, `/play`, `/leave`). UI `src/pages/breakroom/Complots.tsx` (custom cards in the clans' colours). One character per clan: Complots' Duchesse, Assassin, Comtesse, Capitaine, Ambassadeur / Inquisiteur; from Complots 2 only the Bourreau and the Justicier (their powers are in its rules; the other 7 cards' texts are not).
- **Orbi l'extraterrestre**: the channel's public feed (`GET /videos`: YouTube RSS of channel `UCWwdio93JMiS987S0lo6RXg`, read by the server, kept 30 min, last list kept on failure), played in a popup through `youtube-nocookie.com` (CSP `frame-src`; thumbnails from `i.ytimg.com` in `img-src`).

## Roles and Microsoft 365

- Built-in roles (`shared/permissions.ts` SYSTEM_ROLES): **Administrateur principal** (`administrator`, MASTER_ROLE, every right, locked), **Administrateur global** (`global-admin`: everything except MASTER_ONLY — roles, integrations, mail server, `admin.o365`, `outlook.anyMailbox`), **Technicien**, **Lecture seule**. Only a master admin gives the master role or edits / resets / disables a master admin (`assertMasterGuard` in `server/routes/admin.ts`).
- One Entra app registration, two ways: the **organisation access** (application permissions, any mailbox — master admins only) and each technician's **own sign-in** (delegated, OAuth code + PKCE, `server/lib/msauth.ts`, routes `/api/microsoft`, refresh token sealed in `ms_connections`). Graph calls inside `asUser` / `asConnection` (`server/lib/o365.ts`) go out as that person; `user(email)` becomes `me` for their own mailbox.
- Outlook module: own mailbox through the technician's sign-in (`mail_accounts.via = "user"`, linked automatically on sign-in). A mailbox shared with them in Exchange (support@…) is also linked `via = "user"` (delegated `Mail.ReadWrite.Shared` / `Mail.Send.Shared`): Microsoft checks their access at link time and on every call, so a mailbox they cannot open (admin, accounting) is refused (`outlook_no_access`, audited `outlook.link_refused`). Only `outlook.anyMailbox` (master admins) links through the organisation access (`via = "app"`).
- Outlook compose (`ComposeDialog` in `src/pages/outlook/dialogs.tsx`): new / reply / reply all / forward all get To, Cc, Bcc (chips with suggestions, `RecipientInput`), subject (RE:/TR:), a small rich editor (`RichEditor`), the signature, files (drag and drop), importance and read receipt. The server sanitizes every HTML body and signature (`server/lib/mailHtml.ts`, sanitize-html allowlist); replies set recipients/subject/body on the draft Outlook builds (our part above the quote). Signature: profile › Microsoft 365 (`user_preferences.email_signature`, `PUT /api/outlook/signature`). Address book `mail_contacts` (migration 0043): every recipient of a sent email is added (`rememberRecipients`), plus contacts added by hand; `/api/outlook/contacts` is scoped to the signed-in user. The ✨ Corriger button (`AiPolishButton`, `format="html"`) corrects the text written, the signature left out and put back. Replied / forwarded: Graph `singleValueExtendedProperties` PidTagLastVerbExecuted `Integer 0x1081` (102 / 103 / 104) and its time `SystemTime 0x1082`, expanded on the list and the message (`lastVerb`, `lastVerbAt`, icon `VerbIcon`); `respond()` sets them on the original after sending (Graph's send does not). The Outlook page switches between Mail, Calendar (the planning `WeekCalendar` for oneself, needs `tickets.view`) and Contacts.
- Tickets planning calendars: `calendar_links` per technician, chosen by a master admin (`admin.o365`), each `details` or `busy` ("Occupé — name" to anyone but its owner; private events always masked); the one with `push` receives the portal's blocks and day priorities. No link: their own calendar, in detail.

## Running on its own (no Autotask, never sample data)

`ticketsLocal()` is true when Admin › Billets switched to the portal's tickets **or in production while Autotask is not linked**. With no link, `ticketSource()` builds `localTicketSource(localBase)` (`server/lib/localBase.ts`): clients, contacts, contracts (`localCompanies/Contacts/Contracts(…, true)` read the CRM tables directly), products (`store_products`), client lookup by email / phone, charge options and work types (snapshot kept in the tickets mode config at the switch, else defaults). Nothing is read from or written to Autotask, and `demoSource` is never used in production. What the portal makes has ids apart from Autotask's (`server/lib/ids.ts`): clients ≥ 1,000,000,000 (`clients.autotask_id`), contacts and contracts `local-<uuid>`; `adoptLocalIds()` gives one to anything made before. `syncCrm()` then copies nothing (state `source: "local"`, `/api/crm/status` mode `local`, badge "Base locale du portail"), `apply()` never marks native ids "gone", `syncBillables` never drops items copied from Autotask while it is not linked, `exportTickets` returns nothing in production without a link. To leave Autotask: final sync (Integrations › Autotask), switch tickets to the portal, then turn the Autotask integration off.

## Security rules

- Authorization is enforced in the API, never only in the UI. Use `auth(c)` / `requirePermission`; never trust ids or roles sent by the browser.
- Mutations: JSON only + same-origin check (`sameOriginJson`). Sessions are server-side (`sessions` table, cookie holds a random token; DB stores its SHA-256).
- Passwords: scrypt (`server/lib/crypto.ts`), policy ≥ 12 chars. MFA (TOTP) required in production (off by default in dev, `REQUIRE_MFA=true` to test); codes are single-use. MFA secrets sealed with `APP_SECRET`.
- Admin changes are written to `audit_log` via `audit()`. Never log secrets.
- "View as client" (`clientview.use`): the session stores `view_as_client_id`; `loadAuth` swaps `auth.user` to a read-only client identity (`auth.realUser` is the technician). `readOnlyViewAs` blocks every write except `/api/view-as` and logout. Client endpoints must scope by `auth.user.clientId`.
- No secrets in `VITE_*` variables or committed files; `.env` only.
- CSP lives in `server/app.ts` (`secureHeaders`) — fonts are self-hosted (`@fontsource`), no external scripts.
- Graph paths built from browser input go through `safeGraphPath` (in `graph()`): no `.`/`..` segment once decoded, no `%2f`/`%5c`/whitespace. Organisation-access mailboxes (`via = "app"`) need `outlook.anyMailbox` on every request.
- `assertMasterGuard` also protects MASTER_ONLY rights: a non-master cannot give a role carrying one, nor edit/reset/disable someone holding one.
- Password links: built from `PUBLIC_URL` only in production (never the Host header); cleared on password, email or status change (`forgetPasswordLinks`). Client users of an inactive client cannot sign in (`accountUsable`).
- Nobody approves their own timesheet or expense. Invoice creation is one transaction. QuickBooks creations carry a `requestid` (idempotent) and run one at a time. Full Autotask copies use `complete: true` (fail instead of truncating, so nothing looks deleted).
- One app instance only (in-process locks, numbering, background jobs).
